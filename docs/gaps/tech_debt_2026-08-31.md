## GAP-CR-035 — Висящая запись `in_progress` для плейлиста

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1201)
**Location:** `ytd/downloader.py:543` (запись `in_progress`), `ytd/downloader.py:591` (запись `success`) — на момент обнаружения

### Описание

Перед началом загрузки `_download_with_retries` записывает в историю событие `in_progress` с идентификатором, построенным из `opts.url`:

```python
self._record_history(
    {"id": opts.url, "webpage_url": opts.url, "title": None},
    opts,
    status="in_progress",
    started_at=datetime.now(UTC),
)
```

После успешного завершения история пишется по данным yt-dlp: для плейлиста `_build_events` разворачивает `info["entries"]` и создаёт события **на каждый элемент**, с их собственными `video_id`. События для самого URL плейлиста нет — и строка `in_progress`, ключом которой был этот URL, остаётся в базе навсегда.

**Уточнение области после реализации (2026-08-31).** Исходно гэп был описан как проблема плейлистов: предполагалось, что у одиночного видео `opts.url` и `id` дают один ключ. Регрессионный тест показал, что это верно **только для YouTube**:

```
YouTube URL -> yt:ABCDEFGHIJK      YouTube id -> yt:ABCDEFGHIJK   (совпадают)
VK URL      -> https://vk.com/...  VK id      -> -123_456         (различаются)
```

`normalize_history_id` сводит к общему ключу только YouTube-идентификаторы; на VK и других площадках `id` остаётся как есть и не совпадает с нормализованным URL. Значит висящая строка возникала и для **одиночных видео на всех площадках, кроме YouTube**. Исправление сделано общим: оно не привязано к признаку «это плейлист».

### Воспроизведение

Скачивание плейлиста из двух элементов через прямой путь (без интерактива и пауз), yt-dlp подменён заглушкой:

```
строк в истории: 3
  in_progress  https://www.youtube.com/playlist?list=PLprobe  title=None
  success      vid1  title='Video 1'
  success      vid2  title='Video 2'
```

Все элементы скачаны успешно, но родительская строка осталась `in_progress`.

### Влияние

1. **Ложный вопрос при повторном запуске.** Preflight находит запись `in_progress` по URL плейлиста и спрашивает: «Предыдущая загрузка не завершилась успешно. Что сделать? 1) Возобновить 2) Начать заново 0) Пропустить» — для плейлиста, который скачался полностью. Правильным был бы вопрос про уже скачанное (пропустить / перезаписать / другая папка).
2. **Мусор в журнале.** `ytd history` показывает вечно незавершённые загрузки; фильтр `--status in_progress` перестаёт быть полезным как индикатор реально прерванных задач.
3. **Накопление.** Каждый новый URL плейлиста добавляет ещё одну неубираемую строку.

### Критерии приёмки

- После успешной загрузки плейлиста в истории нет строк со статусом `in_progress` по его URL.
- Повторный запуск того же плейлиста задаёт вопрос про уже скачанное, а не про «незавершённую загрузку».
- Регрессионный тест: загрузка плейлиста через заглушку yt-dlp → в `downloads` нет строк со статусом, отличным от финального.

### Что сделано (2026-08-31)

Добавлен `Downloader._close_parent_record(info, opts, status=...)`: он сравнивает нормализованный ключ `opts.url` с ключами уже записанных финальных событий и, если совпадения нет, записывает событие по самому URL с финальным статусом (для плейлиста — с его заголовком и `playlist_id`). Вызывается и на успехе, и в ветке ошибки.

Решение общее по построению: оно исходит не из признака «плейлист», а из факта расхождения ключей, поэтому закрывает и случай одиночного видео на не-YouTube площадках.

Проверка тем же сценарием, что выявил дефект:

```
success  https://www.youtube.com/playlist?list=PLprobe  title='Probe Playlist'
success  vid1  title='Video 1'
success  vid2  title='Video 2'
```

Тесты: `test_playlist_parent_row_is_closed_after_success`, `test_single_video_parent_row_is_closed_when_keys_differ` (VK-подобные идентификаторы), `test_youtube_single_video_has_one_row` (на YouTube по-прежнему ровно одна строка).

Число строк в журнале не выросло: на не-YouTube площадках вторая строка создавалась и раньше — просто оставалась в статусе `in_progress`.

## GAP-CR-036 — Гонка за клавиатурным вводом при возобновлении

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1202)
**Location:** `ytd/pause.py:79` (`_keyboard_listener_windows`), `ytd/pause.py:174` (`_wait_for_resume_windows`), `ytd/pause.py:193` (`_wait_for_resume_unix`) — на момент обнаружения

### Описание

Клавиатуру читают **два независимых потока одновременно**:

1. Фоновый слушатель, запущенный в `enable()`, крутится всё время работы команды и читает символы: `msvcrt.getch()` на Windows, `sys.stdin.read(1)` на Unix.
2. Основной поток внутри `wait_if_paused()` читает те же символы из того же буфера, ожидая `resume_key`.

Слушатель ничего не знает про режим ожидания и продолжает забирать ввод. Символ, доставшийся слушателю, обрабатывается так:

```python
def _handle_listener_key(self, char: str) -> None:
    if char != self.pause_key:
        return
```

То есть `r`, перехваченный слушателем, **молча выбрасывается** и до ожидающего потока не доходит.

### Влияние

Возобновление после паузы срабатывает вероятностно: нажатие `r` может не дать эффекта, и пользователь жмёт клавишу несколько раз. Чем дольше пауза, тем выше шанс, что символ уйдёт «не туда» — оба цикла опрашивают ввод с интервалом 0.1 с. Внешне это выглядит как «зависшая» пауза, хотя процесс жив.

Дефект структурный: два потребителя одного потока ввода, и один из них уничтожает то, что прочитал.

### Статус проверки

Подтверждено чтением кода: `wait_if_paused` не останавливает и не приостанавливает слушатель, а `_stop_listener` в этот момент не выставлен. Автоматическое воспроизведение требует эмуляции TTY и потому не делалось — но механизм однозначен и не зависит от тайминга: достаточно, чтобы слушатель успел прочитать символ первым.

### Критерии приёмки

- В любой момент времени клавиатуру читает ровно один потребитель.
- Нажатие `resume_key` возобновляет загрузку с первого раза.
- Тест на то, что во время ожидания возобновления слушатель не потребляет ввод (проверяется флагом/состоянием, без реального TTY).

### Что сделано (2026-08-31)

Клавиатуру теперь читает только фоновый слушатель. Он же распознаёт `resume_key` (и Enter) при активной паузе и выставляет `threading.Event`; `wait_if_paused` ждёт это событие вместо второго цикла чтения. Методы `_wait_for_resume_windows` и `_wait_for_resume_unix` удалены целиком — вместе с ними исчезли платформенные ветки чтения из режима ожидания.

Fallback на `typer.prompt` теперь срабатывает по более точному условию: слушатель не запущен (не TTY **или** `enable()` не вызывали) — раньше проверялся только TTY, и при незапущенном слушателе ожидание события повисло бы навсегда.

Тесты: `test_listener_key_sets_resume_event`, `test_resume_key_ignored_when_not_paused`, `test_wait_if_paused_returns_when_resume_event_set` (нажатие эмулируется из отдельного потока), `test_wait_if_paused_exits_when_listener_stopped`, `test_wait_if_paused_falls_back_without_listener`. Win32-only тест из BL-1101 больше не нужен: проверка стала платформенно-независимой и выполняется на обеих ОС. `tests/test_intra_video_pause.py` не менялся и проходит.

## GAP-CR-037 — Нет проверки типов в CI

**Severity:** низкая
**Status:** fixed (2026-08-31, BL-1203)
**Location:** `.github/workflows/test.yml`, `pyproject.toml`

### Описание

Кодовая база почти полностью аннотирована: `from __future__ import annotations`, dataclass'ы со `slots`, `TypeAlias` и `Literal` для допустимых значений, `TYPE_CHECKING`-импорты. Но ни один инструмент эти аннотации не проверяет — ни локально, ни в CI. В коде есть точечные `# type: ignore`, поставленные «на всякий случай», и их некому валидировать.

### Влияние

Аннотации сегодня — документация, а не гарантия. Ошибки вида «передали `str` там, где ожидается `Path`» или «забыли `| None`» ловятся только тестами, если тест на этот путь есть. Для проекта, где значительная часть кода — сборка опций и передача данных между слоями, это заметная слепая зона.

### Критерии приёмки

- В CI есть шаг проверки типов, он зелёный.
- Конфигурация зафиксирована в `pyproject.toml`, локальный запуск описан в `DEVELOPMENT.md`.
- Подавления (`ignore`) точечные и объяснённые, а не глобальное отключение правил.

### Что сделано (2026-08-31)

`mypy` в dev-группе, `[tool.mypy]` в `pyproject.toml` (не строгий старт, `files = ["ytd"]`, `warn_unused_ignores = true`), шаг проверки в джобе `lint`.

**Первый прогон дал 14 ошибок; среди них — реальный пользовательский баг.** `typer.BadParameter(..., param_name=...)`: у `click.BadParameter` нет такого параметра, поэтому вместо понятного сообщения пользователь получал сырой traceback:

```
$ ytd history --since не-дата
TypeError: BadParameter.__init__() got an unexpected keyword argument 'param_name'
$ ytd history export --format xml
TypeError: BadParameter.__init__() got an unexpected keyword argument 'param_name'
```

Обе команды воспроизводили падение на реальном CLI. Исправлено на `param_hint`, добавлены тесты `test_history_invalid_since_reports_bad_parameter` и `test_history_export_invalid_format_reports_bad_parameter`. Это ровно тот класс дефекта, ради которого гэп и заводился: код с аннотациями, ошибка в вызове чужого API, тестами не покрыто.

Остальные 13 ошибок: 6 устаревших `# type: ignore` (удалены), неточный тип в `list_downloads` (переписан цикл), 3 обращения к `termios`/`tty` и 3 к `winreg` без платформенных guard'ов.

**Платформенные ветки проверяются под всеми моделями.** Импорты `msvcrt`, `termios`/`tty`, `winreg` видны mypy только под своей платформой, поэтому результат зависел бы от ОС раннера. Вместо подавлений добавлены guard'ы `if sys.platform != "win32": return`, которые mypy понимает и сам исключает недостижимый код, а CI прогоняет три модели:

```
uv run mypy --platform win32   → Success: no issues found in 31 source files
uv run mypy --platform linux   → Success
uv run mypy --platform darwin  → Success
```

Модель darwin дополнительно выявила расхождение: `_detect_mac_browser` был объявлен `-> str | None`, хотя всегда возвращает строку, а вызывающий код ожидает `str`. Аннотация сужена.

## GAP-CR-038 — Нет метрики покрытия тестами

**Severity:** низкая
**Status:** fixed (2026-08-31, BL-1204)
**Location:** `pyproject.toml`, `.github/workflows/test.yml`

### Описание

Тестов 121, они детерминированы и не требуют сети — но неизвестно, какая доля кода ими выполняется. «121 тест» само по себе не отвечает на вопрос, покрыт ли, например, путь `playlist_batch` или ветки классификации сетевых ошибок.

### Влияние

Нельзя обоснованно ответить, где тестов не хватает. При добавлении фич легко нарастить количество тестов вокруг уже покрытых мест и не заметить, что новый модуль не выполняется ни разу. После декомпозиции `execute_download` (BL-1105) это особенно актуально: девять новых модулей, и часть их веток проверяется только косвенно.

### Критерии приёмки

- Покрытие измеряется в CI и печатается в лог прогона.
- Зафиксирован порог, равный текущему уровню (не «красивое число»), падение ниже порога роняет сборку.
- В `DEVELOPMENT.md` описан локальный запуск с отчётом.

### Что сделано (2026-08-31)

`pytest-cov` в dev-группе, `[tool.coverage.*]` с `branch = true` и исключением `TYPE_CHECKING`. Измеренное покрытие — **68.04%**, порог выставлен на **66%** (на два пункта ниже, чтобы обычные колебания не роняли сборку). Считается только на ubuntu: платформенные ветки дают разный результат на Windows и Linux, и общий порог на обеих ОС был бы хрупким.

Первый отчёт сразу показал, где тестов нет — это вход для будущих задач, а не повод поднимать порог:

| Модуль | Покрытие | Что не покрыто |
|--------|----------|----------------|
| `workflows/network.py` | 21% | диалог восстановления после потери сети |
| `workflows/playlist_resume.py` | 33% | выбор «продолжить / удалить / вручную» |
| `workflows/info_fetch.py` | 36% | ветки повтора и пропуска |
| `interactive.py` | 40% | большинство диалогов |
| `workflows/history_prompts.py` | 45% | ветки решений по истории |
| `browser_detect.py` | 15% | платформенные детекторы |

Общая картина закономерна: не покрыты интерактивные ветки, требующие эмуляции диалогов. Ядро загрузки и оркестрации покрыто заметно лучше — `context.py` 100%, `types.py` 100%, `download_one.py` 93%, `single_video.py` 93%, `config.py` 89%.

## GAP-CR-039 — `main` не защищён обязательными проверками

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1205 — выбран вариант A)
**Location:** настройки репозитория GitHub (вне кода)

### Описание

CI зелёный и информативный, но ничего не гарантирует: `git push origin main` проходит независимо от результата проверок. За время Maintenance 1.2 в `main` ушло шесть прямых пушей — каждый раз результат проверялся уже постфактум.

### Влияние

CI работает как отчёт, а не как барьер. Сломанный коммит попадает в `main` и остаётся там до тех пор, пока кто-то не посмотрит на статус вручную. Для проекта, который специально завёл двухплатформенную матрицу ради ловли регрессий, это обесценивает половину пользы.

### Требуется решение владельца

Включение обязательных проверок на GitHub означает переход на PR-поток: прямой push в защищённую ветку невозможен, поскольку проверки должны отработать до попадания коммита в ветку. Репозиторий раньше уже жил в PR-модели (ветки `codex/*` мержились через PR), но последние циклы шли прямыми пушами.

Это компромисс между скоростью одиночной работы и надёжностью, и выбирает его владелец — см. варианты в [дизайне](../design_tech_debt_2026-08-31.md#d-5-защита-ветки-main-gap-cr-039).

### Критерии приёмки

- Решение принято и зафиксировано в бэклоге (включаем защиту / оставляем как есть с обоснованием).
- Если включаем: `test (ubuntu-latest)`, `test (windows-latest)`, `lint` в списке обязательных проверок; описан рабочий поток в `DEVELOPMENT.md`.

### Что сделано (2026-08-31)

**Решение владельца: вариант A — защита с обязательными проверками и PR-потоком.** Правило для `main`: обязательны `test (ubuntu-latest)`, `test (windows-latest)`, `lint`; требуется PR перед merge; запрещены force-push и удаление ветки; включён `required_linear_history`. Ревью не требуется — работа одиночная.

**`enforce_admins` включён по результату проверки.** Изначально правило было создано с `enforce_admins: false` — как escape hatch для владельца. Проверка прямым push показала, что при этом защита не срабатывает вовсе: администратор (он же единственный автор) спокойно пушит в `main`, и барьера нет. После включения `enforce_admins` push отклоняется:

```
remote: - 3 of 3 required status checks are expected.
 ! [remote rejected] main -> main (protected branch hook declined)
```

## GAP-CR-040 — Интеграционные тесты не выполняются нигде

**Severity:** низкая
**Status:** fixed (2026-08-31, BL-1206 — выбран вариант A)
**Location:** `tests/test_integration.py`

### Описание

Два интеграционных теста включаются переменной `YTD_IT_URL` и без неё пропускаются. Переменная не задаётся ни в CI, ни в документации разработчика как регулярный шаг — то есть тесты не выполнялись ни разу за оба цикла сопровождения и в каждом прогоне видны как `2 skipped`.

### Влияние

Единственная проверка того, что ytd действительно умеет разговаривать с живой площадкой, фактически не работает. При этом она создаёт видимость покрытия: строка `2 skipped` в отчёте читается как «есть интеграционные тесты», хотя их результат никому не известен.

### Критерии приёмки

- Принято и зафиксировано решение: удалить, запускать по расписанию/вручную или явно оставить ручным инструментом.
- Если остаются — в `DEVELOPMENT.md` описано, как и когда их запускать.
- Строка `skipped` в обычном прогоне перестаёт быть немым сигналом (объяснена в документации).

### Что сделано (2026-08-31)

**Решение владельца: вариант A — оставить ручным инструментом и задокументировать.** В `DEVELOPMENT.md` добавлен раздел «Интеграционные тесты»: команды запуска для PowerShell и bash, что именно проверяется (`ytd info --json` и `ytd download --dry-run`, без скачивания файлов), когда запускать (перед релизом или при подозрении на поломку экстрактора yt-dlp) и почему их нет в CI — результат зависит от доступности площадки и её anti-bot защиты, поэтому регулярные прогоны давали бы красные сборки не по вине кода.

Строка `2 skipped` в обычном прогоне больше не немая: она объяснена в документации разработчика.

## GAP-CR-009 (перенесён) — JSONL и SQLite как два источника правды

**Severity:** низкая
**Status:** fixed (2026-08-31, BL-1207 — выбран вариант B)

### Описание

Метаданные пишутся и в JSONL (`save_metadata`), и в SQLite (`history_db`). Роли разведены в `docs/usage.md`, однократный импорт из JSONL реализован, но модель данных остаётся двойной: одна и та же загрузка порождает записи в двух хранилищах с разной схемой и разным жизненным циклом.

В прошлом ревью гэп сознательно закрыли статусом `documented` — как осознанный design debt. Он остаётся в этом качестве, но с момента того решения появилось обстоятельство: `ytd history export --format jsonl` уже умеет отдавать JSONL из SQLite, то есть исходная потребность (построчный архив для grep/jq) закрывается без второго хранилища.

### Критерии приёмки

- Принято решение: оставить как есть / сделать JSONL опциональным по умолчанию / отказаться от JSONL в пользу экспорта.
- Решение и его обоснование зафиксированы; при изменении поведения описан путь миграции.

### Что сделано (2026-08-31)

**Решение владельца: вариант B — JSONL опционален и по умолчанию выключен.** `save_metadata` в `AppConfig` и `DownloadOptions` теперь `None`; строка в `config.example.yaml` закомментирована с пояснением; README и `docs/usage.md` описывают изменение и путь возврата.

Обоснование: `ytd history export --format jsonl` даёт тот же построчный дамп из SQLite, поэтому второе хранилище перестало быть необходимым. Полный отказ (вариант C) сломал бы существующие пайплайны и всё равно потребовал бы сохранить импорт.

**Совместимость.** Поведение возвращается одной строкой конфига (`save_metadata: data/meta.jsonl`) или переменной `YTD_SAVE_METADATA`. Импорт из уже существующего JSONL при первом создании базы работает как раньше — `import_from_jsonl` не тронут, тесты `tests/test_history_import.py` без изменений.

Побочный эффект: тесты больше не создают `data/meta.jsonl` в рабочем каталоге при запуске из корня репозитория — раньше значение по умолчанию приводило к записи файла на каждом прогоне.
