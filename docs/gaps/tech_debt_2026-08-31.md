## GAP-CR-035 — Висящая запись `in_progress` для плейлиста

**Severity:** средняя
**Status:** open
**Location:** `ytd/downloader.py:543` (запись `in_progress`), `ytd/downloader.py:591` (запись `success`)

### Описание

Перед началом загрузки `_download_with_retries` записывает в историю событие `in_progress` с идентификатором, построенным из `opts.url`:

```python
self._record_history(
    {"id": opts.url, "webpage_url": opts.url, "title": None},
    opts,
    status="in_progress",
    started_at=datetime.now(UTC),
)
```

После успешного завершения история пишется по данным yt-dlp: для плейлиста `_build_events` разворачивает `info["entries"]` и создаёт события **на каждый элемент**, с их собственными `video_id`. События для самого URL плейлиста нет — и строка `in_progress`, ключом которой был этот URL, остаётся в базе навсегда.

Для одиночного видео проблемы нет: `opts.url` нормализуется в тот же ключ (`yt:<id>`), что и событие успеха, поэтому строка обновляется.

### Воспроизведение

Скачивание плейлиста из двух элементов через прямой путь (без интерактива и пауз), yt-dlp подменён заглушкой:

```
строк в истории: 3
  in_progress  https://www.youtube.com/playlist?list=PLprobe  title=None
  success      vid1  title='Video 1'
  success      vid2  title='Video 2'
```

Все элементы скачаны успешно, но родительская строка осталась `in_progress`.

### Влияние

1. **Ложный вопрос при повторном запуске.** Preflight находит запись `in_progress` по URL плейлиста и спрашивает: «Предыдущая загрузка не завершилась успешно. Что сделать? 1) Возобновить 2) Начать заново 0) Пропустить» — для плейлиста, который скачался полностью. Правильным был бы вопрос про уже скачанное (пропустить / перезаписать / другая папка).
2. **Мусор в журнале.** `ytd history` показывает вечно незавершённые загрузки; фильтр `--status in_progress` перестаёт быть полезным как индикатор реально прерванных задач.
3. **Накопление.** Каждый новый URL плейлиста добавляет ещё одну неубираемую строку.

### Критерии приёмки

- После успешной загрузки плейлиста в истории нет строк со статусом `in_progress` по его URL.
- Повторный запуск того же плейлиста задаёт вопрос про уже скачанное, а не про «незавершённую загрузку».
- Регрессионный тест: загрузка плейлиста через заглушку yt-dlp → в `downloads` нет строк со статусом, отличным от финального.

## GAP-CR-036 — Гонка за клавиатурным вводом при возобновлении

**Severity:** средняя
**Status:** open
**Location:** `ytd/pause.py:79` (`_keyboard_listener_windows`), `ytd/pause.py:174` (`_wait_for_resume_windows`), `ytd/pause.py:193` (`_wait_for_resume_unix`)

### Описание

Клавиатуру читают **два независимых потока одновременно**:

1. Фоновый слушатель, запущенный в `enable()`, крутится всё время работы команды и читает символы: `msvcrt.getch()` на Windows, `sys.stdin.read(1)` на Unix.
2. Основной поток внутри `wait_if_paused()` читает те же символы из того же буфера, ожидая `resume_key`.

Слушатель ничего не знает про режим ожидания и продолжает забирать ввод. Символ, доставшийся слушателю, обрабатывается так:

```python
def _handle_listener_key(self, char: str) -> None:
    if char != self.pause_key:
        return
```

То есть `r`, перехваченный слушателем, **молча выбрасывается** и до ожидающего потока не доходит.

### Влияние

Возобновление после паузы срабатывает вероятностно: нажатие `r` может не дать эффекта, и пользователь жмёт клавишу несколько раз. Чем дольше пауза, тем выше шанс, что символ уйдёт «не туда» — оба цикла опрашивают ввод с интервалом 0.1 с. Внешне это выглядит как «зависшая» пауза, хотя процесс жив.

Дефект структурный: два потребителя одного потока ввода, и один из них уничтожает то, что прочитал.

### Статус проверки

Подтверждено чтением кода: `wait_if_paused` не останавливает и не приостанавливает слушатель, а `_stop_listener` в этот момент не выставлен. Автоматическое воспроизведение требует эмуляции TTY и потому не делалось — но механизм однозначен и не зависит от тайминга: достаточно, чтобы слушатель успел прочитать символ первым.

### Критерии приёмки

- В любой момент времени клавиатуру читает ровно один потребитель.
- Нажатие `resume_key` возобновляет загрузку с первого раза.
- Тест на то, что во время ожидания возобновления слушатель не потребляет ввод (проверяется флагом/состоянием, без реального TTY).

## GAP-CR-037 — Нет проверки типов в CI

**Severity:** низкая
**Status:** open
**Location:** `.github/workflows/test.yml`, `pyproject.toml`

### Описание

Кодовая база почти полностью аннотирована: `from __future__ import annotations`, dataclass'ы со `slots`, `TypeAlias` и `Literal` для допустимых значений, `TYPE_CHECKING`-импорты. Но ни один инструмент эти аннотации не проверяет — ни локально, ни в CI. В коде есть точечные `# type: ignore`, поставленные «на всякий случай», и их некому валидировать.

### Влияние

Аннотации сегодня — документация, а не гарантия. Ошибки вида «передали `str` там, где ожидается `Path`» или «забыли `| None`» ловятся только тестами, если тест на этот путь есть. Для проекта, где значительная часть кода — сборка опций и передача данных между слоями, это заметная слепая зона.

### Критерии приёмки

- В CI есть шаг проверки типов, он зелёный.
- Конфигурация зафиксирована в `pyproject.toml`, локальный запуск описан в `DEVELOPMENT.md`.
- Подавления (`ignore`) точечные и объяснённые, а не глобальное отключение правил.

## GAP-CR-038 — Нет метрики покрытия тестами

**Severity:** низкая
**Status:** open
**Location:** `pyproject.toml`, `.github/workflows/test.yml`

### Описание

Тестов 121, они детерминированы и не требуют сети — но неизвестно, какая доля кода ими выполняется. «121 тест» само по себе не отвечает на вопрос, покрыт ли, например, путь `playlist_batch` или ветки классификации сетевых ошибок.

### Влияние

Нельзя обоснованно ответить, где тестов не хватает. При добавлении фич легко нарастить количество тестов вокруг уже покрытых мест и не заметить, что новый модуль не выполняется ни разу. После декомпозиции `execute_download` (BL-1105) это особенно актуально: девять новых модулей, и часть их веток проверяется только косвенно.

### Критерии приёмки

- Покрытие измеряется в CI и печатается в лог прогона.
- Зафиксирован порог, равный текущему уровню (не «красивое число»), падение ниже порога роняет сборку.
- В `DEVELOPMENT.md` описан локальный запуск с отчётом.

## GAP-CR-039 — `main` не защищён обязательными проверками

**Severity:** средняя
**Status:** open
**Location:** настройки репозитория GitHub (вне кода)

### Описание

CI зелёный и информативный, но ничего не гарантирует: `git push origin main` проходит независимо от результата проверок. За время Maintenance 1.2 в `main` ушло шесть прямых пушей — каждый раз результат проверялся уже постфактум.

### Влияние

CI работает как отчёт, а не как барьер. Сломанный коммит попадает в `main` и остаётся там до тех пор, пока кто-то не посмотрит на статус вручную. Для проекта, который специально завёл двухплатформенную матрицу ради ловли регрессий, это обесценивает половину пользы.

### Требуется решение владельца

Включение обязательных проверок на GitHub означает переход на PR-поток: прямой push в защищённую ветку невозможен, поскольку проверки должны отработать до попадания коммита в ветку. Репозиторий раньше уже жил в PR-модели (ветки `codex/*` мержились через PR), но последние циклы шли прямыми пушами.

Это компромисс между скоростью одиночной работы и надёжностью, и выбирает его владелец — см. варианты в [дизайне](../design_tech_debt_2026-08-31.md#d-5-защита-ветки-main-gap-cr-039).

### Критерии приёмки

- Решение принято и зафиксировано в бэклоге (включаем защиту / оставляем как есть с обоснованием).
- Если включаем: `test (ubuntu-latest)`, `test (windows-latest)`, `lint` в списке обязательных проверок; описан рабочий поток в `DEVELOPMENT.md`.

## GAP-CR-040 — Интеграционные тесты не выполняются нигде

**Severity:** низкая
**Status:** open
**Location:** `tests/test_integration.py`

### Описание

Два интеграционных теста включаются переменной `YTD_IT_URL` и без неё пропускаются. Переменная не задаётся ни в CI, ни в документации разработчика как регулярный шаг — то есть тесты не выполнялись ни разу за оба цикла сопровождения и в каждом прогоне видны как `2 skipped`.

### Влияние

Единственная проверка того, что ytd действительно умеет разговаривать с живой площадкой, фактически не работает. При этом она создаёт видимость покрытия: строка `2 skipped` в отчёте читается как «есть интеграционные тесты», хотя их результат никому не известен.

### Критерии приёмки

- Принято и зафиксировано решение: удалить, запускать по расписанию/вручную или явно оставить ручным инструментом.
- Если остаются — в `DEVELOPMENT.md` описано, как и когда их запускать.
- Строка `skipped` в обычном прогоне перестаёт быть немым сигналом (объяснена в документации).

## GAP-CR-009 (перенесён) — JSONL и SQLite как два источника правды

**Severity:** низкая
**Status:** documented (перенесён из [ревью 2026-05-25](./code_review_2026-05-25.md))

### Описание

Метаданные пишутся и в JSONL (`save_metadata`), и в SQLite (`history_db`). Роли разведены в `docs/usage.md`, однократный импорт из JSONL реализован, но модель данных остаётся двойной: одна и та же загрузка порождает записи в двух хранилищах с разной схемой и разным жизненным циклом.

В прошлом ревью гэп сознательно закрыли статусом `documented` — как осознанный design debt. Он остаётся в этом качестве, но с момента того решения появилось обстоятельство: `ytd history export --format jsonl` уже умеет отдавать JSONL из SQLite, то есть исходная потребность (построчный архив для grep/jq) закрывается без второго хранилища.

### Критерии приёмки

- Принято решение: оставить как есть / сделать JSONL опциональным по умолчанию / отказаться от JSONL в пользу экспорта.
- Решение и его обоснование зафиксированы; при изменении поведения описан путь миграции.
