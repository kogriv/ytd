## GAP-CR-026 — `wait_if_paused` вешает процесс на Windows без TTY

**Severity:** высокая
**Status:** fixed (2026-08-31, BL-1101)
**Location:** `ytd/pause.py:143` (`wait_if_paused`), `ytd/pause.py:163` (`_wait_for_resume_windows`) — на момент обнаружения
**Проявление:** `tests/test_pause.py:29` зависает бесконечно; полный `pytest` на Windows не завершается

### Описание

`wait_if_paused` выбирает бэкенд ожидания только по платформе:

```python
if sys.platform == "win32":
    self._wait_for_resume_windows()
else:
    self._wait_for_resume_unix()
```

Unix-ветка (`pause.py:181`) начинается с проверки интерактивности и при не-TTY уходит в безопасный fallback:

```python
def _wait_for_resume_unix(self) -> None:
    if not self._stdin_is_interactive():
        self._wait_for_resume_prompt()
        return
```

Windows-ветка такой проверки **не содержит**: единственный fallback — `ImportError` при импорте `msvcrt`, которого на Windows не бывает. Дальше идёт бесконечный цикл `while True` с `msvcrt.kbhit()`, который в среде без консольного ввода (перенаправленный stdin, CI, запуск из другого процесса, тестовый прогон) не получит ни одного нажатия и никогда не завершится.

### Влияние

1. **Продуктовое.** На Windows при запуске без интерактивной консоли (планировщик задач, CI, pipe, вызов из скрипта) любой запрос паузы приводит к «вечному» зависанию процесса без диагностики. Пауза может быть включена не только флагом, но и конфигом (`pause_between_videos`, `intra_video_pause`), то есть попасть в такой запуск неявно.
2. **Инженерное.** Полный прогон `pytest` на Windows не завершается: разработчик не может получить результат тестов без ручного `--deselect` или снятия процесса. Это скрывает и остальные ошибки (см. GAP-CR-027, обнаруженный только после deselect).

Асимметрия усугубляется тем, что `enable()` (`pause.py:40`) корректно проверяет интерактивность и предупреждает пользователя — то есть контракт «без TTY клавиши не работают» уже заявлен, но в `wait_if_paused` не соблюдён.

### Воспроизведение

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_pause.py -q   # виснет после 2 пройденных тестов
```

Тест `test_wait_if_paused_clears_flag_with_prompt_fallback` мокает `sys.stdin.isatty → False` и `typer.prompt`, ожидая ветку `_wait_for_resume_prompt`. На Linux он проходит, на Windows — зависает.

### Ожидаемое поведение

Проверка интерактивности stdin должна выполняться **до** выбора платформенного бэкенда: в не-интерактивной среде обе платформы одинаково уходят в `_wait_for_resume_prompt()`.

### Критерии приёмки

- `wait_if_paused` при `sys.stdin.isatty() == False` не входит в цикл `msvcrt.kbhit()` ни на одной платформе.
- `tests/test_pause.py` полностью проходит на Windows и Linux.
- Полный `pytest` на Windows завершается без `--deselect`.

### Что сделано (2026-08-31)

Проверка `_stdin_is_interactive()` поднята в `wait_if_paused` до платформенной развилки (`ytd/pause.py:156`): без TTY обе платформы уходят в `_wait_for_resume_prompt()`. Дублирующая проверка удалена из `_wait_for_resume_unix`. Оба цикла ожидания клавиши переведены на `while not self._stop_listener.is_set()` с ожиданием на самом событии — `disable()` теперь разрывает ожидание вместо того, чтобы оставлять процесс висеть.

Тесты: `test_wait_if_paused_uses_key_backend_on_tty` (на TTY используется платформенный бэкенд, prompt не вызывается), `test_wait_for_resume_windows_exits_when_listener_stopped` (skipif не-win32). `tests/test_pause.py` — 7 passed на Windows; полный прогон завершается без `--deselect`.

## GAP-CR-027 — Тест импорта истории завязан на POSIX-разделитель путей

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1102)
**Location:** `tests/test_history_import.py:46`, `tests/test_history_import.py:52` — на момент обнаружения

### Описание

Тест сравнивает сохранённый путь со строкой, содержащей прямой слэш:

```python
assert first["file_path"].endswith("downloads/first.mp4")
```

`HistoryStore` сохраняет путь через `_normalize_path` → `str(Path(value))` (`ytd/history/storage.py:42`), то есть в нативном для ОС виде. На Windows получается `downloads\first.mp4`, и ассерт падает.

```
E  AssertionError: assert False
E   +  where False = 'downloads\\first.mp4'.endswith('downloads/first.mp4')
```

### Влияние

Единственный падающий тест на платформе разработки. Сам продукт работает корректно — дефект в тестовом ожидании, но он создаёт постоянный «красный» прогон, к которому привыкают и перестают замечать реальные регрессии.

Отдельно стоит зафиксировать: нормализация путей в нативный вид — **осознанное** поведение (`file_path` показывается пользователю в `ytd history show` и должен быть кликабельным в его ОС). Менять продукт под тест не нужно.

### Критерии приёмки

- Ассерты сравнивают пути платформенно-независимо (через `Path` или `as_posix()`).
- `tests/test_history_import.py` зелёный на Windows и Linux.

### Что сделано (2026-08-31)

Ассерты переведены на сравнение `Path(...) == Path(...)`; рядом оставлен комментарий, что нативная нормализация `file_path` в продукте намеренная и менять её не нужно. Аудит остальных тестов на строковые сравнения путей: `tests/test_downloader_history.py:121,124` и `tests/test_utils.py:28` сравнивают только имя файла и расширение — разделитель в них не участвует, правки не требуются.

## GAP-CR-028 — CI не покрывает Windows

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1103 + BL-1104)
**Location:** `.github/workflows/test.yml:10` — на момент обнаружения

### Описание

Единственная джоба CI выполняется на `ubuntu-latest`. При этом:

- основная платформа разработки и эксплуатации — Windows (в коде есть Windows-специфичные ветки: `msvcrt`, обход `OSError [Errno 22]`, `sanitize_filename` под правила Windows, `browser_detect._detect_windows_browser` через `winreg`);
- документация и примеры написаны преимущественно под PowerShell;
- два дефекта (GAP-CR-026, GAP-CR-027) существуют только на Windows и дошли до `main` именно потому, что CI их не видит.

Дополнительно: в прогоне нет ограничения времени на тест — зависание (GAP-CR-026) на Windows-раннере привело бы к «висящей» джобе до глобального таймаута, а не к внятному падению.

### Влияние

Обратная связь CI не репрезентативна для реальной платформы. Класс дефектов «работает на Linux, ломается на Windows» систематически проходит мимо проверок.

### Критерии приёмки

- Матрица `os: [ubuntu-latest, windows-latest]` в тестовой джобе; линт достаточно оставить на одной ОС.
- Подключён `pytest-timeout` (или эквивалент), зависший тест падает по таймауту, а не блокирует прогон.
- Обе джобы зелёные после закрытия GAP-CR-026 и GAP-CR-027.

### Что сделано (2026-08-31)

**BL-1104 закрыт:** `pytest-timeout==2.4.0` в dev-группе, `timeout = 60` и `timeout_method = "thread"` в `[tool.pytest.ini_options]`. Механизм проверен на реальном зависании до исправления GAP-CR-026: прогон упал по таймауту с трассировкой, указывающей на конкретную строку цикла ожидания.

**BL-1103 закрыт:** тестовая джоба переведена на `strategy.matrix.os: [ubuntu-latest, windows-latest]` с `fail-fast: false`, ruff вынесен в отдельную джобу `lint`. Первый прогон матрицы (`33342899092`) — success: `test (ubuntu-latest)` 96 passed / 3 skipped за 31.4 с, `test (windows-latest)` 97 passed / 2 skipped за 35.9 с, `lint` passed. Общее время прогона выросло с ~47 с до ~57 с (джобы идут параллельно).

Расхождение в счётчиках ожидаемое: `test_wait_for_resume_windows_exits_when_listener_stopped` помечен `skipif(sys.platform != "win32")`. Обе платформы собирают одинаковые 99 тестов, Windows-результат в CI совпал с локальным прогоном — класс дефектов «работает на Linux, ломается на Windows» теперь ловится автоматически.

## GAP-CR-029 — `execute_download` — новый монолит

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1105)
**Location:** `ytd/workflows/download_command.py:49` (функция `execute_download`, файл 999 строк) — на момент обнаружения

### Описание

BL-104 из предыдущего ревью сократил `cli.py` с ~1680 до 394 строк, но оркестрация целиком переехала в одну функцию: `execute_download` занимает ~950 строк и содержит:

- разбор CLI-оверрайдов и загрузку конфига;
- выбор плейлиста при нескольких кандидатах;
- preflight-опрос истории;
- инициализацию `PauseController`;
- пять веток загрузки с разной глубиной вложенности (до 6 уровней);
- четыре вложенные функции-замыкания: `read_urls_from_file:133`, `fetch_info_with_prompt:225`, `prompt_history_decision:256`, `prepare_unified_entry:552`, `resolve_playlist_download_indices:403`, `prepare_individual_entry:678`, `prepare_pause_entry:824`;
- агрегацию итогов и маппинг в exit-коды.

Замыкания захватывают порядка пятнадцати переменных внешней области (`cfg`, `dl`, `dry_run`, `logger`, `history_available`, `chosen_format`, `target_height`, `strategy`, `quality_suffix`, `use_numbering`, `prefix_template`, `overwrite_all`, `current_output_dir`, `failed` через `nonlocal` и др.), из-за чего их нельзя ни протестировать по отдельности, ни переиспользовать.

Это признано в предыдущем ревью как частичное решение: GAP-CR-001 и GAP-CR-014 имеют статус `mitigated`, а не `fixed`.

### Влияние

- Любая правка UX требует навигации по функции длиной с модуль; управляющий поток с `continue` в цикле по URL и флагом `skip_post_processing` хрупок — исторический баг двойной загрузки возник именно на нём.
- Ветки нельзя покрыть unit-тестами — только сквозными прогонами через `CliRunner`.
- `nonlocal failed` внутри `prepare_*` смешивает подсчёт ошибок анализа и ошибок загрузки.

### Критерии приёмки

- `execute_download` — не более ~150 строк: подготовка контекста и диспетчеризация по стратегиям.
- Сценарии плейлиста и одиночного видео живут в отдельных модулях и принимают явный контекст вместо замыканий.
- Существующие regression-тесты (`tests/test_playlist_regression.py`, `tests/test_interactive_config.py`) проходят без изменений.

### Что сделано (2026-08-31)

`execute_download` — **112 строк** (21 из них — сигнатура): подготовка контекста и цикл диспетчеризации. `download_command.py` — 294 строки вместо 999; самый крупный модуль `workflows/` теперь 207 строк.

Новые модули: `context.py` (`DownloadContext`, `DownloadTotals`), `url_sources.py`, `info_fetch.py`, `download_one.py` (`EntrySetup`, `build_options`, `download_single_url`), `single_video.py`, `playlist_interactive.py`, `playlist_unified.py`, `playlist_per_video.py`, `playlist_resume.py`.

Все сценарии имеют единую сигнатуру `run(ctx, url, decision) -> DownloadTotals` и выбираются один раз через `select_scenario`. Флаг `skip_post_processing` удалён: сценарий владеет своим путём целиком, поэтому «провалиться» в общий путь после поштучной загрузки структурно невозможно — регрессия doublesave закрыта архитектурно, а не флагом.

`download_entry_with_retry` расширен опциональными `loading_message=None`, `skip_message`, `show_error_hints`, `error_message` — это позволило переиспользовать его на прямом пути вместо второй копии цикла сетевых повторов.

Тесты: **110 passed, 2 skipped**; добавлен `tests/test_workflow_scenarios.py` (13 тестов на `select_scenario`, `collect_urls`, `choose_interactive_playlist`, `is_effective_playlist`, `DownloadTotals`, `DownloadContext.output_dir`). Regression-тесты плейлиста и интерактива не менялись. Смоук-прогон CLI подтвердил прежние сообщения и коды возврата.

Побочная находка при переносе кода — [GAP-CR-034](#gap-cr-034--typerexit-гасится-широким-except-в-интерактивных-сценариях).

## GAP-CR-030 — Мёртвая ветка повторного опроса истории

**Severity:** низкая
**Status:** fixed (2026-08-31, BL-1106 в рамках BL-1105)
**Location:** `ytd/workflows/download_command.py:902-908` — на момент обнаружения

### Описание

```python
decision = preflight_decision
if decision is None:
    decision = prompt_history_decision(...)
```

`preflight_decision` присваивается на `:338` и никогда не бывает `None`: список решений либо заполняется в preflight-цикле (`:273-286`), либо добивается заглушками `HistoryDecision(proceed=True)` (`:294`), либо берётся значение по умолчанию `HistoryDecision(proceed=True)` при выходе индекса за границы (`:341`). Условие всегда ложно, вызов `prompt_history_decision` недостижим.

### Влияние

Само по себе безвредно, но:

- создаёт ложное впечатление, что на общем пути есть второй, более поздний опрос истории (с уточнённым `history_video_id`, полученным из метаданных), — а его нет;
- переменная `history_video_id`, вычисляемая на `:352` и уточняемая на `:379` и `:778`, на этом пути больше нигде не используется.

Нужно решить сознательно: удалить мёртвый код или реализовать задуманный уточняющий опрос по резолвнутому идентификатору.

### Критерии приёмки

- Недостижимых веток в `execute_download` нет.
- Принятое решение (удалить / реализовать) зафиксировано в дизайн-доке и отражено в коде.

### Что сделано (2026-08-31)

Ветка удалена вместе с переменной `history_video_id`, которая существовала только ради неё. Решение «удалить, а не реализовывать» обосновано в дизайн-доке (D-5): preflight уже спрашивает пользователя по каждой ссылке до начала загрузок, а для элементов плейлиста уточнённый опрос по реальному `video_id` выполняется в `process_playlist_entries`. Повторный вопрос про ту же ссылку был бы регрессом UX.

## GAP-CR-031 — `urls.local.txt` с личными ссылками в репозитории

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1107)
**Location:** `urls.local.txt` (отслеживался git), `.gitignore:67-69`

### Описание

Файл озаглавлен «Локальный файл со ссылками для загрузки (не попадает в Git)», но фактически он **закоммичен** и присутствует в `git ls-files`. Правило игнорирования в `.gitignore` закомментировано:

```
# Local URLs files (do not commit real links)
# urls.local.txt
```

Файл содержит реальные ссылки на YouTube и VK с пометками о содержимом.

### Влияние

- Расхождение заявленного и фактического поведения: пользователь, редактирующий «локальный» файл, не ожидает, что его ссылки уйдут в публичный репозиторий.
- Приватность: список просматриваемого контента публикуется вместе с кодом.
- Ссылки уже находятся в истории коммитов — удаление из индекса не убирает их из прошлых ревизий.

### Критерии приёмки

- Рабочий файл со ссылками не отслеживается git; правило в `.gitignore` активно.
- В репозитории есть безопасный пример (`urls.example.txt`) и упоминание его в README.
- Решение по очистке истории коммитов принято владельцем репозитория и зафиксировано (переписывание истории — потенциально ломающая операция, выполняется только по явному указанию).

### Что сделано (2026-08-31)

`git rm --cached urls.local.txt` (файл сохранён на диске); правило в `.gitignore:68-69` активировано и расширено на `urls.*.local.txt`; добавлен `urls.example.txt`; в README указано, что рабочий файл локальный.

**Решение владельца: историю git не переписываем.** Ссылки остаются в прошлых ревизиях.

**Исправление обоснования (2026-08-31).** Изначально здесь было записано «репозиторий приватный, риск ограничен участниками с доступом» — это неверно: `kogriv/ytd` **публичный** (`gh repo view` → `visibility=PUBLIC`). Решение перепроверено на честных вводных и оставлено прежним по другим причинам:

## GAP-CR-034 — `typer.Exit` гасится широким `except` в интерактивных сценариях

**Severity:** средняя
**Status:** fixed (2026-08-31, BL-1110; найден в тот же день при выполнении BL-1105)
**Location:** `ytd/workflows/single_video.py:63`, `ytd/workflows/playlist_interactive.py:60`, `ytd/workflows/playlist_batch.py:79` (исторически — `download_command.py:760`, `:793`, `:886`)

### Описание

`typer.Exit` наследуется от `RuntimeError`, то есть является обычным `Exception`:

```
>>> [c.__name__ for c in typer.Exit.__mro__]
['Exit', 'RuntimeError', 'Exception', 'BaseException', 'object']
```

Интерактивные сценарии оборачивают получение метаданных в широкий `except Exception`, чтобы при неудачном разборе плейлиста продолжить с настройками по умолчанию. Но в этот же блок попадает `typer.Exit(1)`, который поднимает `fetch_info`, когда пользователь в диалоге сетевой ошибки выбрал **«3) Завершить программу»**.

### Влияние

Явная команда пользователя остановить работу не выполняется: вместо завершения печатается warning «продолжим с настройками по умолчанию», и загрузка идёт дальше — по общему пути, где для плейлиста будет скачан весь плейлист целиком. Пользователь, отменивший операцию из-за проблем с сетью или VPN, получает ровно то, что пытался предотвратить.

Дефект существовал до BL-1105; при декомпозиции поведение сохранено намеренно, чтобы рефакторинг не смешивал перенос кода с изменением семантики. В коде проставлены `TODO(GAP-CR-034)`.

### Ожидаемое поведение

`typer.Exit` (и `click.exceptions.Abort`) пробрасываются наружу; широкий `except Exception` ловит только реальные ошибки разбора.

```python
except typer.Exit:
    raise
except Exception as exc:  # noqa: BLE001
    ctx.logger.warning(...)
```

### Критерии приёмки

- Выбор «завершить программу» в диалоге сетевой ошибки завершает команду с кодом 1 из любого сценария.
- Тест на каждый из трёх сценариев: `fetch_info` поднимает `typer.Exit`, сценарий его не гасит.
- `TODO(GAP-CR-034)` из кода удалены.

### Что сделано (2026-08-31)

В `single_video.run`, `playlist_interactive.run` и `playlist_batch.run` добавлена ветка `except (typer.Exit, typer.Abort): raise` перед широким обработчиком. `typer.Abort` (это `click.Abort`) включён по той же причине: он тоже наследуется от `RuntimeError` и поднимается при Ctrl+C или EOF в диалоге, то есть тоже означает отмену пользователем.

В `execute_download` добавлена обработка `typer.Abort` наравне с `KeyboardInterrupt`: вместо «✗ Ошибка: » с пустым текстом (Abort не несёт сообщения) выводится «✗ Прервано пользователем», код возврата 1. Проверено смоук-прогоном: сетевая ошибка + EOF в диалоге теперь даёт понятное сообщение вместо пустого.

Тесты: 6 параметризованных проверок «сценарий не гасит остановку» (три сценария × `Exit`/`Abort`) и 3 проверки «обычная ошибка разбора по-прежнему приводит к загрузке с настройками по умолчанию» — вторые нужны, чтобы исправление не пережало fallback. Всего 119 passed, 2 skipped. `TODO(GAP-CR-034)` из кода удалены.
