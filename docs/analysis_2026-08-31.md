### Применённые паттерны

- **Facade** — `Downloader` скрывает `yt_dlp.YoutubeDL`.
- **Builder** — `build_ydl_opts` собирает опции из `DownloadOptions` + `AppConfig`.
- **Strategy** — стратегии подбора качества `econom` / `rich` (`utils.find_best_quality_match`).
- **Template method (через callback)** — `process_playlist_entries` принимает `prepare_entry` как точку вариативности для трёх сценариев плейлиста.
- **Dependency injection** — `HistoryStore` передаётся в `Downloader`, module-level API работает через default store.
- **Dataclass-контракты** — `SingleVideoSetupResult`, `HistoryDecision`, `PreparedEntry`, `EntryDownloadResult`, `PlaylistEntriesResult`.

## Ключевые потоки выполнения

### `ytd download`

`cli.cmd_download` → `workflows.download_command.execute_download`:

1. Перенастройка кодировки stdout/stderr (`errors="replace"`) — защита от `UnicodeEncodeError` в Windows-консоли.
2. `load_config()` → `merge_cli_overrides()` (CLI > ENV > файл > дефолты).
3. Разрешение tri-state `--interactive/--no-interactive` через `interactive_by_default`.
4. `initialize_history(cfg, logger)` — создание БД, однократный импорт JSONL.
5. Сбор ссылок: позиционный URL + `--urls-file` (строки с `#` игнорируются).
6. Автодетект плейлистов `looks_like_playlist_url` (по `playlist` в path или параметру `list=`); при нескольких кандидатах в интерактиве — меню выбора одного плейлиста.
7. **Preflight-история**: по каждому URL — `prompt_history_decision`; полностью скачанные отсеиваются, остальные получают решение (overwrite / другая папка).
8. Инициализация `PauseController` (между видео и/или внутри файла).
9. Выбор ветки на каждый URL:
   - **интерактив + плейлист, режим 1** «единые настройки»: анализ форматов первого элемента → меню качества → суффикс → нумерация → стратегия fallback → перезапись → подтверждение маски → `process_playlist_entries` с пер-элементным подбором высоты;
   - **интерактив + плейлист, режим 2** «каждое видео отдельно»: `run_single_video_interactive_setup` внутри `prepare_entry`;
   - **интерактив + одиночное видео**: `run_single_video_interactive_setup`;
   - **не интерактив + плейлист + паузы**: поштучный проход `process_playlist_entries`;
   - **общий путь**: один `DownloadOptions` на URL, плейлист отдаётся yt-dlp целиком.
10. Флаг `skip_post_processing` предотвращает повторный проход по URL плейлиста после поштучной загрузки (регрессия doublesave).
11. Агрегация: `total_files` / `failed` → exit-код `0` / `1` / `2`.

### `Downloader.download`

`_download_with_retries` — внешний цикл (перезапуск после intra-video паузы) + внутренний цикл попыток:

1. `build_ydl_opts` (пересобирается на каждой попытке — важно для `no_progress`).
2. Запись `in_progress` в историю.
3. Один `extract_info(url, download=True)` (после BL-401 — без предварительного вызова).
4. Резолв путей: из progress-hook `finished`, иначе `prepare_filename`.
5. Сохранение метаданных в JSONL.
6. Запись `success` (пропускается, если история уже писалась инкрементально по хукам).
7. Обработка исключений: intra-video пауза → ожидание → перезапуск; `OSError 22` на Windows → повтор без прогресс-бара; сетевая ошибка → `NetworkUnavailableError`; иначе backoff и повтор.

### `ytd history`

`history_root` собирает фильтры (`--status`, `--limit`, `--since`, `--playlist`) в `ctx.obj`; без подкоманды печатает таблицу; `show` — карточка с двухэтапным lookup (нормализованный ID → сырой ID → URL); `export` — JSONL или CSV в stdout.

## Конфигурация

- **Приоритет:** CLI > ENV (`YTD_*`) > YAML-файл > дефолты `AppConfig`.
- **Поиск файла:** явный `config_path` → `$YTD_CONFIG` → `./ytd.config.yaml`. Файлы `config.yaml` / `config.yml` намеренно **не** читаются.
- **ENV-карта:** 21 ключ (`config.py:28`), типизация по полям (bool-парсер, int/float, список субтитров через запятую).
- **Валидация:** `quality`, `audio_format`, `video_format`, `cookies_from_browser` — по фиксированным множествам; `proxy` — по схеме (`http/https/socks4/socks5/socks5h`) и наличию хоста.
- **Нормализация:** относительные пути → абсолютные от CWD; каталоги `output`, `save_metadata.parent`, `history_db.parent` создаются заранее.

Полный набор опций описан в `config.example.yaml` (73 строки, все поля прокомментированы).

## История загрузок

Две сущности с разными ролями:

| Хранилище | Файл | Роль |
|-----------|------|------|
| SQLite | `data/history.db` | рабочий журнал: `ytd history`, промпты «пропустить/перезаписать», фильтры, экспорт |
| JSONL | `data/meta.jsonl` | построчный архив метаданных yt-dlp для grep/jq/внешних скриптов + источник однократного импорта |

- **Ключ строки** — нормализованный идентификатор (`normalize_history_id`): YouTube → `yt:<11 символов>` (из `v=`, `youtu.be/`, `shorts|embed|live`), иначе канонизированный URL (нижний регистр хоста, схлопнутые слэши, отсортированный query).
- **Схема** `downloads`: `video_id` PK, `url`, `title`, `status`, `started_at`, `finished_at`, `file_path`, `error`, `playlist_id`, `playlist_title`, `retry_count`, `last_action`; миграция недостающих колонок через `ALTER TABLE`.
- **Upsert** `ON CONFLICT(video_id) DO UPDATE` с `COALESCE` — новые значения не затирают уже известные непустые.
- **Надёжность**: `journal_mode=WAL`, `busy_timeout=5000`, `timeout=5.0`.
- **Импорт JSONL** выполняется только если таблица пуста; распознаёт `id/video_id/display_id/url`, пути из `filepath/filename/_filename/requested_downloads[]`, временные метки из `epoch/timestamp/release_timestamp/upload_date`.
- **Инкрементальная запись**: по каждому хуку `finished` пишется `success` для конкретного элемента; батч-запись пропускается, если инкрементальная уже была (`_incremental_history`).

## Интерактивный UX

- **Одиночное видео:** ШАГ 1 качество (меню из доступных высот + «лучшее» + «только аудио») → ШАГ 2 имя файла (суффикс качества / префикс / полное переименование) → ШАГ 3 проверка существующих файлов по `[video_id]` в имени с предложением перезаписи.
- **Плейлист:** информация о плейлисте (первые 10 элементов) → выбор режима (единые настройки / по одному / отмена) → для режима 1: качество, суффикс, нумерация (`{N:02d}_` или пользовательский шаблон), стратегия fallback качества, перезапись, предпросмотр итогового имени и подтверждение.
- **Resume плейлиста:** `analyze_playlist_progress` находит уже скачанные элементы → `prompt_playlist_resume` предлагает продолжить с первого недостающего / удалить и скачать заново / выбрать вручную маской (`3-7`, `5-`, `-4`, `all`, `все`).
- **Паузы:** `p` — запрос паузы, `r` или Enter — продолжение; между элементами и/или внутри файла.

## Оценка состояния

**Сильные стороны.**

- Декомпозиция после Maintenance 1.1 состоялась: `cli.py` — тонкий слой, оркестрация в `workflows/`, циклических import нет.
- Контракты вынесены в dataclass'ы со `slots`, типы валидируются на границе конфига.
- История загрузок продумана: нормализация идентификаторов, WAL, двухэтапный lookup, инкрементальная запись, миграции колонок.
- Обработка отказов ориентирована на реальную эксплуатацию: сеть, anti-bot, кодировки консоли, особенности Windows-консоли.
- Тесты не требуют сети, детерминированы, покрывают регрессии по именам задач бэклога.
- Дисциплина документации: gap-док → бэклог → трассировочная матрица → отметки в коде.

**Слабые стороны.**

- Матрица платформ в CI не соответствует основной платформе разработки — два Windows-дефекта дошли до `main`.
- Монолит переехал из `cli.py` в `workflows/download_command.py`; вложенные замыкания (`prepare_unified_entry`, `resolve_playlist_download_indices`, `prepare_individual_entry`, `prepare_pause_entry`) удерживают ~15 переменных внешней области.
- Нет защиты от зависаний в тестах (`pytest-timeout` не подключён) — один зависший тест блокирует весь прогон.
- Часть документов (`devplan*`) не входит в цикл обновления и расходится с кодом.

**Вывод.** Проект в хорошем состоянии для личной и рабочей эксплуатации; критичных дефектов в основном сценарии загрузки не обнаружено. Найденные гэпы — про кроссплатформенную дисциплину качества и поддерживаемость, а не про корректность загрузки.
