## Принципы и рамки

1. **Сначала дефекты, потом ворота качества.** GAP-CR-035 и GAP-CR-036 видны пользователю; остальное — инфраструктура, которая должна ловить такие дефекты в будущем.
2. **Пороги ставим по факту, а не по красоте.** Порог покрытия равен измеренному уровню; цель — не дать ему упасть, а не изобразить «80%».
3. **Новые инструменты входят зелёными.** Проверка типов и покрытие подключаются только вместе с приведением кода в соответствие: сборка не должна «временно краснеть».
4. **Решения владельца не подменяются кодом.** Три пункта (защита ветки, судьба интеграционных тестов, судьба JSONL) требуют выбора владельца; дизайн даёт варианты и рекомендацию, но не выполняет их молча.
5. **Ничего не ломаем в поведении.** Единственное намеренное изменение — исчезновение ложного вопроса про «незавершённую загрузку» и надёжное срабатывание клавиши возобновления.

## D-1. Закрытие родительской записи истории (GAP-CR-035)

### Проблема

`in_progress` пишется по ключу `opts.url`, а `success` — по ключам элементов плейлиста. Родительская строка не закрывается никогда.

### Варианты

| Вариант | Суть | Оценка |
|---------|------|--------|
| **A. Закрывать родительскую запись** (рекомендуется) | После успеха дополнительно записать событие для `opts.url` со статусом `success`, заголовком плейлиста и его `playlist_id` | Журнал показывает плейлист как единицу работы; повторный запуск задаёт правильный вопрос («уже скачано») |
| B. Не писать `in_progress` для плейлистов | При `opts.playlist=True` пропускать стартовую запись | Теряется след прерванной загрузки — ровно то, ради чего запись делалась |
| C. Удалять родительскую строку после успеха | `DELETE` по ключу | Журнал теряет информацию о плейлисте; удаление данных ради косметики |

Выбран **A**: он не только убирает мусор, но и делает поведение осмысленным — плейлист становится полноценной записью журнала.

### Решение

В `Downloader` добавляется запись «родительского» события при завершении, если загрузка была плейлистной:

```python
# ytd/downloader.py

def _record_playlist_parent(self, info: Any, opts: DownloadOptions, *, status: str) -> None:
    """Закрыть запись, созданную по opts.url на старте: у плейлиста свой ключ."""
    if not isinstance(info, dict) or not info.get("entries"):
        return  # одиночное видео — ключ совпадает с элементом, запись уже обновлена
    self._record_history(
        {
            "id": opts.url,
            "webpage_url": opts.url,
            "title": info.get("title"),
            "playlist_id": info.get("id") or info.get("playlist_id"),
            "playlist_title": info.get("title"),
        },
        opts,
        status=status,
        finished_at=datetime.now(UTC),
    )
```

Вызывается там же, где пишется итог: после успеха — со `status="success"`, в ветке ошибки — со `status="failed"` (сейчас ошибочная ветка уже пишет событие по `history_info`, но при пустом `info` теряет привязку к URL).

Важная деталь: `_build_events` для словаря **без** `entries` строит ровно одно событие, поэтому передаём плоский словарь, а не сам `info` с элементами — иначе снова получим события по элементам.

### Тесты

- `test_playlist_parent_row_is_closed_after_success` — загрузка плейлиста через заглушку yt-dlp; в `downloads` нет строк со статусом `in_progress`, есть строка по URL плейлиста со `success` и заголовком.
- `test_single_video_history_has_one_row` — регрессия: для одиночного видео по-прежнему одна строка.
- Существующие `tests/test_downloader_history.py` не меняются.

## D-2. Единственный читатель клавиатуры (GAP-CR-036)

### Проблема

Слушатель пауз и `wait_if_paused` одновременно читают один поток ввода; символ, доставшийся слушателю, выбрасывается.

### Варианты

| Вариант | Суть | Оценка |
|---------|------|--------|
| **A. Один читатель — слушатель** (рекомендуется) | Слушатель распознаёт и `pause_key`, и `resume_key`; ожидание реализуется через `threading.Event`, а не через второй цикл чтения | Устраняет класс ошибки целиком; минус две платформенные функции чтения |
| B. Приостанавливать слушатель на время ожидания | Флаг `_suspended`, слушатель пропускает чтение | Правка меньше, но два читателя остаются — на другом переходе состояния гонка вернётся |

Выбран **A**: он убирает саму возможность конкуренции, а заодно сокращает `pause.py` — исчезают `_wait_for_resume_windows` и `_wait_for_resume_unix`.

### Решение

```python
class PauseController:
    def __init__(self, ...):
        ...
        self._resume_requested = threading.Event()

    def _handle_listener_key(self, char: str) -> None:
        if char == self.resume_key or char in {"\r", "\n"}:
            if self._pause_requested.is_set():
                self._resume_requested.set()
            return
        if char != self.pause_key:
            return
        self._pause_requested.set()
        ...  # сообщение как сейчас

    def wait_if_paused(self) -> None:
        if not self._pause_requested.is_set():
            return
        ...  # печать шапки паузы как сейчас
        if not self._stdin_is_interactive() or not self._enabled:
            self._wait_for_resume_prompt()
            return
        safe_secho(f"Нажмите '{self.resume_key}' для возобновления или Ctrl+C для выхода...", ...)
        while not self._resume_requested.wait(timeout=0.1):
            if self._stop_listener.is_set():
                break
        self._resume_requested.clear()
        self._clear_pause_and_resume()
```

Проверка `not self._enabled` в дополнение к TTY существенна: если слушатель не запущен (например, `enable()` не вызывали), ждать события бессмысленно — нужен prompt-fallback.

### Что удаляется

`_wait_for_resume_windows`, `_wait_for_resume_unix` и их платформенные импорты внутри функций. `_wait_for_resume_prompt` остаётся как единственный fallback для не-интерактивной среды.

### Тесты

- `test_listener_key_sets_resume_event` — `resume_key` при активной паузе выставляет событие.
- `test_resume_key_ignored_when_not_paused` — вне паузы `resume_key` ничего не делает.
- `test_wait_if_paused_returns_when_resume_event_set` — ожидание завершается по событию (без TTY, поток эмулируется вызовом `_handle_listener_key` из другого потока).
- `test_wait_if_paused_falls_back_without_listener` — при выключенном слушателе используется prompt.
- Существующие тесты `tests/test_pause.py`, включая win32-only, обновляются под новую схему.

## D-3. Проверка типов в CI (GAP-CR-037)

### Выбор инструмента

**mypy** — потому что конфигурация живёт в `pyproject.toml` рядом с ruff, а строгость наращивается по модулям. Pyright потребовал бы node-окружение в CI ради того же результата.

### Решение

```toml
[dependency-groups]
dev = [
  "pytest>=9",
  "pytest-timeout>=2.3",
  "mypy>=1.11",
  "ruff>=0.9",
]

[tool.mypy]
python_version = "3.14"
files = ["ytd"]
warn_unused_ignores = true      # ловит устаревшие "# type: ignore"
warn_redundant_casts = true
no_implicit_optional = true
check_untyped_defs = true

[[tool.mypy.overrides]]
module = ["yt_dlp.*"]
ignore_missing_imports = true   # у yt-dlp нет типовых стабов
```

Старт намеренно не строгий: без `disallow_untyped_defs` и `strict`. Задача первого шага — получить зелёный базовый уровень и включить его в CI, а не переписать аннотации разом.

Шаг в CI добавляется в существующую джобу `lint` (проверка типов платформенно-независима, второй прогон на Windows не нужен):

```yaml
      - name: Ruff lint
        run: uv run ruff check .

      - name: Type check
        run: uv run mypy
```

`tests/` в `files` не включены сознательно: тестовые заглушки намеренно частично типизированы, и их проверка дала бы шум без пользы.

### Порядок работ

1. Прогнать локально, зафиксировать список ошибок.
2. Исправить настоящие несоответствия; для неустранимых поставить точечные `# type: ignore[код]` с комментарием.
3. Только после зелёного локального прогона добавить шаг в CI.

Если объём ошибок окажется большим, допустимо временно сузить `files` до подмножества модулей и расширять его отдельными задачами — но это фиксируется в бэклоге явно, а не молча.

## D-4. Измерение покрытия (GAP-CR-038)

### Решение

```toml
[dependency-groups]
dev = [..., "pytest-cov>=5", ...]

[tool.coverage.run]
source = ["ytd"]
branch = true

[tool.coverage.report]
show_missing = true
exclude_lines = [
  "pragma: no cover",
  "if TYPE_CHECKING:",
  "raise NotImplementedError",
]
```

Порог **не выдумывается**: сначала измеряем текущее покрытие, затем ставим `--cov-fail-under` на 1–2 пункта ниже измеренного, чтобы обычные колебания не роняли сборку, а падение на десятки процентов — роняло.

CI (только на ubuntu, чтобы не удваивать шум; вторая платформа проверяет поведение, а не покрытие):

```yaml
      - name: Run tests
        run: uv run pytest -q --cov --cov-report=term-missing --cov-fail-under=<измеренное>
```

Отчёт `term-missing` печатает незакрытые строки прямо в лог — по нему видно, какие ветки новых модулей `workflows/` не выполняются.

### Ожидаемый побочный результат

Первый же отчёт покажет, насколько реально покрыты сценарии после BL-1105. Если обнаружатся модули с низким покрытием, это становится входом для отдельных задач, а не поводом сразу поднимать порог.

## D-5. Защита ветки `main` (GAP-CR-039)

### Суть выбора

Обязательные проверки на GitHub означают, что коммит попадает в `main` только после зелёного прогона. Технически это требует PR-потока: прямой `git push origin main` в защищённую ветку с обязательными проверками невозможен, поскольку проверки должны отработать **до** появления коммита в ветке.

| Вариант | Что даёт | Чего стоит |
|---------|----------|------------|
| **A. Защита + PR-поток** (рекомендуется) | CI становится барьером; в `main` не попадает красное | Каждое изменение через ветку и PR; для одиночной работы — лишний шаг (`gh pr create --fill` + merge) |
| B. Защита без обязательных проверок (только запрет force-push и удаления ветки) | Страховка от разрушительных операций | CI остаётся отчётом; красное по-прежнему доезжает |
| C. Оставить как есть | Максимальная скорость | Всё, что описано в GAP-CR-039 |

Рекомендация — **A**, с оговоркой: репозиторий уже жил в этой модели (ветки `codex/*` мержились через PR), а поток «ветка → PR → merge» в этом цикле фактически применялся и вручную. Разница только в том, что merge будет ждать зелёного CI.

Минимальная настройка при выборе A (Settings → Branches → Add rule для `main`):

- Require a pull request before merging (без обязательного ревью — работа одиночная);
- Require status checks to pass: `test (ubuntu-latest)`, `test (windows-latest)`, `lint`;
- Require branches to be up to date before merging;
- запретить force-push и удаление ветки.

### Что делает эта задача в коде

Ничего. Задача сводится к решению владельца, настройке в интерфейсе GitHub и описанию потока в `DEVELOPMENT.md`. Именно поэтому в бэклоге у неё явный пункт «решение принято» как критерий приёмки.

## D-6. Судьба интеграционных тестов (GAP-CR-040)

| Вариант | Оценка |
|---------|--------|
| **A. Оставить ручным инструментом + документировать** (рекомендуется) | Дёшево и честно: тесты остаются как способ проверить живую площадку перед релизом, `DEVELOPMENT.md` объясняет, как их запустить и почему они skipped |

Вариант B можно рассмотреть позже отдельной задачей, если появится необходимость раннего обнаружения поломок yt-dlp; тогда джоба должна быть отдельной, не блокирующей, с `continue-on-error: true`.

## D-7. Решение по JSONL и SQLite (GAP-CR-009)

### Контекст изменился

Гэп был закрыт как `documented` в мае. С тех пор появился `ytd history export --format jsonl`, который отдаёт JSONL из SQLite. Исходная причина существования второго хранилища (построчный архив для grep/jq) теперь закрывается экспортом.

| Вариант | Суть | Оценка |
|---------|------|--------|
| A. Оставить как есть | Ноль работы | Двойная модель данных сохраняется, дублирование записи на каждой загрузке |
| **B. Сделать JSONL опциональным, по умолчанию выключенным** (рекомендуется) | `save_metadata: null` по умолчанию; пишется только если пользователь задал путь | Обратная совместимость сохраняется, дублирование исчезает у всех, кто не просил; импорт из JSONL остаётся для миграции |
| C. Отказаться от JSONL полностью | Максимальная простота | Ломает существующие пайплайны пользователей; импорт старых данных придётся сохранять всё равно |

Рекомендация — **B**. Что меняется:

- `AppConfig.save_metadata: Path | None = None` (было `Path("data/meta.jsonl")`);
- `config.example.yaml`: строка `save_metadata` закомментирована с пояснением «включите, если нужен построчный архив; журнал ведётся в SQLite»;
- `docs/usage.md`: таблица ролей дополняется примечанием, что JSONL теперь опционален, а `ytd history export` покрывает ту же потребность;
- импорт `import_from_jsonl` при первом создании базы **сохраняется** — он нужен именно тем, у кого файл уже есть.

Риск: пользователь, полагавшийся на автоматический JSONL, после обновления его не получит. Поэтому изменение сопровождается заметкой в README и в разделе usage — и это единственное место в спринте, где меняется значение по умолчанию.

## Риски и их снижение

| Риск | Вероятность | Влияние | Снижение |
|------|-------------|---------|----------|
| mypy выдаёт десятки ошибок и блокирует спринт | средняя | среднее | Не строгий старт; при большом объёме — сузить `files` и расширять отдельными задачами, зафиксировав это в бэклоге |
| Порог покрытия оказывается хрупким (колеблется от прогона к прогону) | низкая | низкое | Порог на 1–2 пункта ниже измеренного; покрытие считается только на ubuntu |
| Переход на PR-поток замедляет работу | средняя | низкое | `gh pr create --fill` + `gh pr merge --squash` — два вызова; при неприемлемости выбирается вариант B или C |
| Изменение `save_metadata` по умолчанию удивит пользователя | средняя | среднее | Заметка в README и usage; импорт из JSONL сохраняется; поведение возвращается одной строкой конфига |
| Правка `pause.py` ломает intra-video паузу | низкая | среднее | Существующие тесты `test_intra_video_pause.py` не меняются и остаются критерием; ручная проверка `p`/`r` на реальной загрузке |
